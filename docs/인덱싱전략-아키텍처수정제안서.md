# SpagetiKnot 함수 인덱싱 전략 — 코드 아키텍처 수정 제안서

> 작성 기준: QA 개발자 검토 결과 + 콜 그래프 다이어그램 뷰어 용도 기준
> 대상 파일: `src/extension/references.ts`, `src/extension/parser.ts`

---

## 1. 현황 요약

현재 아키텍처는 두 축으로 구성된다.

- **파서 (parser.ts)**: 언어별 정규식 패턴으로 함수 선언을 추출
- **엣지 해석 (references.ts)**: 언어 계열별 2개 전략(import 기반 / 근접성 기반)으로 호출 관계 판단

전체적인 설계 방향은 탄탄하나, QA 검토에서 다음 두 그룹의 문제가 식별되었다.

---

## 2. 과한 부분 (Over-engineered) — 단순화 제안

### 2-A. `SWIFT_FRAMEWORK_TYPES` 정적 레지스트리 → 대문자 휴리스틱으로 대체

**현황**  
100개 이상의 Apple 프레임워크 타입명을 하드코딩. visionOS, SwiftData, Swift 6 신규 API 추가 시 누락.

**문제**  
- `swiftExternalChainType()`이 레지스트리 히트 없이 프레임워크 타입을 오탐 없이 통과
- 유지보수 부담이 높고 세트 크기 대비 실질 효용이 낮음

**제안**  
Swift 파일에서 호출 체인의 직접 수신자(immediate receiver)가 **대문자로 시작하면 외부 타입**으로 간주한다.  
프로젝트 내 타입은 `typeFileMap`에 등록되므로, 거기에 없는 대문자 수신자 = 외부로 판단.

```typescript
// references.ts — swiftExternalChainType 교체안
function isSwiftExternalReceiver(
  line: string,
  callStart: number,
  typeFileMap: Map<string, string[]>,
): string | null {
  const prefix = line.slice(0, callStart);
  const chainTypes = prefix.match(/\b([A-Z]\w*)(?:\.\w+)*\.$/);
  if (!chainTypes) return null;
  const typeName = chainTypes[1];
  // 대문자 수신자가 프로젝트 파일 basename에 없으면 → 외부
  const lc = typeName.toLowerCase();
  if (!typeFileMap.has(lc)) return typeName;
  return null;
}
```

`SWIFT_FRAMEWORK_TYPES` Set과 `swiftExternalChainType()` 함수 전체를 삭제.  
`typeFileMap`을 `findReferences()` 내에서 이미 생성하므로 추가 비용 없음.

**기대 효과**: 코드 ~110줄 감소, 신규 프레임워크 API 자동 처리.

### 2-B. `extractComment()` 복잡도 축소

**현황**  
위/아래 최대 30줄 스캔 + JSDoc 블록 파싱 + modifier 건너뛰기.

**문제**  
콜 그래프 뷰어에서 주석은 팝오버의 **보조 정보**. 주석 추출 실패는 노드 표시에 영향 없음.

**제안**  
`extractCommentAbove()`와 `extractCommentBelow()` 탐색 범위를 각 **5줄**로 축소.  
JSDoc 블록 파싱(내부 `j` 루프)은 유지하되 최대 `funcLine - 10` 이내로 제한.

```typescript
// 현재
for (let i = funcLine - 1; i >= Math.max(0, funcLine - 20); i--) {
// 변경
for (let i = funcLine - 1; i >= Math.max(0, funcLine - 5); i--) {
```

성능상 영향은 미미하나 코드 명확성이 높아짐.

### 2-C. `extractParams()` 타입 제거 로직 간소화

**현황**  
TS 콜론 어노테이션, Java/C# `Type name` 패턴, 기본값 `= ...` 제거까지 처리.

**문제**  
팝오버에는 파라미터 **이름만** 표시. 타입 파싱이 틀려도 UI에 미치는 영향은 최소.

**제안**  
다단계 파싱 대신 단순 정리로 교체.

```typescript
// 교체안: 타입 어노테이션과 기본값을 단일 regex로 제거
function cleanParamName(raw: string): string {
  return raw
    .trim()
    .replace(/[:\?].*$/, '')   // TS: name: Type  →  name
    .replace(/=.*$/, '')       // 기본값 제거
    .split(/\s+/).pop() ?? ''; // "Type name" 패턴에서 마지막 단어
}
```

## 3. 부족한 부분 (Under-engineered) — 우선순위별 개선 제안

### 우선순위 HIGH

#### 3-A. `patternsForFile` ↔ `getFileLanguage` 분류 불일치 해소

**현황**  
`parser.ts`의 `patternsForFile()`는 `.c/.h/.cpp`에 `PATTERNS_JAVA_CS_CPP`를 반환.  
`references.ts`의 `getFileLanguage()`는 `.c/.h/.cpp`를 `'other'`로 분류 → 근접성 기반 해석.

**문제**  
파싱 언어 기준과 엣지 해석 언어 기준이 서로 다른 파일에서 각자 관리. 동기화가 깨지기 쉬움.

**제안 (아키텍처 변경)**  
언어 분류를 `parser.ts`에서 단일 소스로 관리하고 export.

```typescript
// parser.ts (신규 export)
export type FileLanguage = 'python' | 'jsTs' | 'swift' | 'go' | 'javaLike' | 'cLike' | 'other';

export function getFileLanguage(filePath: string): FileLanguage {
  switch (path.extname(filePath).toLowerCase()) {
    case '.py':                       return 'python';
    case '.ts': case '.tsx':
    case '.js': case '.jsx':          return 'jsTs';
    case '.swift':                    return 'swift';
    case '.go':                       return 'go';
    case '.java': case '.cs':         return 'javaLike';
    case '.c': case '.h':
    case '.cpp': case '.cc':          return 'cLike'; // 신규 분류 추가
    default:                          return 'other';
  }
}
```

```typescript
// references.ts — import해서 사용
import { FunctionInfo, getFileLanguage, FileLanguage } from './parser';
```

`patternsForFile()`도 내부적으로 `getFileLanguage()`를 사용하도록 리팩터.  
`cLike`는 근접성 기반 해석(Swift/Go와 동일 경로)으로 처리.

### 우선순위 MEDIUM

#### 3-D. `isInsideString()` — 템플릿 리터럴 처리 추가

**현황**  
홀수 개의 `"` 또는 `'` 카운팅 방식. 백틱 템플릿 리터럴 미처리.

**제안**  
백틱을 `"` 및 `'`와 동일하게 처리.

```typescript
function isInsideString(line: string, pos: number): boolean {
  let inSingle = false, inDouble = false, inBacktick = false;
  for (let i = 0; i < pos; i++) {
    const ch = line[i];
    if (ch === "'" && !inDouble && !inBacktick)  inSingle  = !inSingle;
    if (ch === '"' && !inSingle && !inBacktick)  inDouble  = !inDouble;
    if (ch === '`' && !inSingle && !inDouble)    inBacktick = !inBacktick;
  }
  return inSingle || inDouble || inBacktick;
}
```

정규식 리터럴(`/pattern/`)은 문자열로 오탐될 수 있으나, 콜 그래프 맥락에서 `/foo(/g` 같은 패턴이 함수명과 충돌하는 사례는 극히 드물어 현 시점에서는 수용 가능한 한계.

---

#### 3-E. `PATTERNS_JAVA_CS_CPP` — 패키지-private / 비멤버 함수 지원

**현황**  
`public|private|protected|...` 접근 제어자를 필수로 요구.  
Java 패키지-private(수식어 없는 메서드), C++ 비멤버 함수는 인덱싱 불가.

**제안**  
접근 제어자를 **선택적(optional)**으로 변경하되, 반환 타입을 앵커로 활용.

```typescript
// 현행: 접근 제어자 필수
/\b(?:public|private|protected|static|final|virtual|override|abstract)\s+[\w<>\[\],\s]+\s+([a-zA-Z_]\w*)\s*\(/g

// 개선안: 접근 제어자 선택적, 반환 타입 필수
/^[ \t]*(?:(?:public|private|protected|static|final|virtual|override|abstract)\s+)*[\w<>\[\]]+\s+([a-zA-Z_]\w*)\s*\(/gm
```

오탐 위험이 있으므로, **Java/C# 전용 패턴**(`PATTERNS_JAVA`)과 **C/C++ 전용**(`PATTERNS_CPP`)을 분리하는 것이 장기적으로 안전.

#### 3-F. `getSubdirectories()` — 2단계 탐색으로 확장

**현황**  
루트의 직속 하위 디렉터리 20개만 표시. `src/features/auth/` 같은 심층 모듈은 미표시.

#### 3-H. `findEnclosingFunction()` end-line 추가 (장기 개선)

**현황**  
"직전 선언 함수 = 소유자" 휴리스틱. 중첩 함수나 연속 단함수 패턴에서 오귀속 발생.

**근본 원인**  
`FunctionInfo`에 `endLine` 필드가 없어 정규식만으로 함수 경계를 알 수 없음.

**제안 (단계적 적용)**

1단계: `FunctionInfo`에 `endLine?: number` 추가.  
2단계: `parseFunctions()`에서 중괄호 카운팅으로 `endLine` 추산.

```typescript
// parser.ts — FunctionInfo 타입 확장
export interface FunctionInfo {
  name: string;
  filePath: string;
  line: number;
  endLine?: number; // 신규: 정규식 기반 추산, 확실하지 않으면 undefined
  kind: 'function' | 'method' | 'arrow' | 'export';
  params: string[];
  comment: string;
}
```

3단계: `findEnclosingFunction()`에서 `endLine`이 있으면 범위 내 포함 여부 우선 확인.

인덴트 기반 Python이나 중괄호 기반 언어 모두 적용 가능.  
`endLine`이 없는 함수는 현행 휴리스틱으로 폴백.

## 5. 변경하지 않는 부분

다음은 현행 그대로 유지 권장.

- **5단계 Priority 엣지 해석 (JS/TS/Python)**: 논리 구조가 탄탄하고 false-edge 방지 핵심
- **근접성 기반 Step A~E (Swift/Go/Java)**: receiver 추론 → same-dir 순서 적절
- **ExternalCall 분리 타입**: 그래프 엣지와 외부 호출을 분리 보관하는 설계는 올바름
- **deduplicateEdges / deduplicateExternalCalls**: 현행 로직 유지
- **extractCommentAbove의 modifier 건너뛰기 로직**: Swift/Java에서 정확하므로 유지
- **언어별 패턴 분리 구조**: 오탐 방지 핵심, 교체 불필요
